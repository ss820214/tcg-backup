# 0バト v1.2.1 — 経済データのサーバー権限移行（作業ブランチ）

## 現状（2026-11-09）

v1.2.0 の `public/gacha.js` はブラウザで乱数抽選し、ユーザー本人の `users/{uid}` にジェム・天井・所持カードを書き戻す。対戦報酬 `recordMatchResult` と初回プロフィール初期化、運営ギフト受取もブラウザから更新する。この状態では、クライアント改変者の不正ガチャ・報酬・所持カード改ざんを防げない。

このブランチは **本番の振る舞いを一切変更しない**。カットオーバー用の `security/v1.2.1_users_server_authority.rules.part` と静的検査を準備する段階。ここに記載したルールは、バックエンド移行前に **絶対に公開しない**。

## 移行が完了したとみなす条件

1. 信頼できるサーバー（無料枠のある外部 Worker 等）で Firebase ID token の署名・issuer・audience・期限を正しく検証する。ブラウザから渡された uid やカード抽選結果を信用しない。
2. サーバーでガチャ排出テーブル、料金、天井、カードプール、乱数を管理し、ジェム減算・所持数増加・天井進行・リクエストID重複排除を **原子的** に確定する。古いブラウザ版の直接書込を許さない。
3. 対戦報酬はサーバーで対戦参加者・終了状態・重複支払い・勝敗妥当性を検証する。単にクライアントの「勝利」を信じる API に置換するのは無意味。
4. 新規ユーザー初期残高、初期カード、運営ギフト・カード配布・Growth を信頼できるサーバー経由に移す。既存の所持物と残高を移行時に初期化しない。
5. `users` 以外の `rooms`, `decks`, `tierBoards`, 履歴などにも無制限更新権限がないか Firestore Emulator で検証する。
6. 本番ルールの全文を保存し、旧版からの差分を確認した後に、`/users/{uid}` ルールを差し替える。既存の別 `match` の `allow` が OR 結合で突破口にならないことを検証する。
7. 2端末と旧ブラウザ版を含め、通常ログイン・新規登録・ガチャ1/10連・天井・カード付与・対戦勝敗・報酬・運営配布・デッキ保存を本番相当環境で検証する。
8. サーバー停止・無料枠到達時は「安全に失敗」させ、不正なクライアント更新へフォールバックしない。

## 対応表

| 処理 | 現状 | 信頼側への移行後 |
| --- | --- | --- |
| `ensureUserProfile` | ブラウザで初期付与・更新 | サーバーで UID 検証と一回限りの初期付与 |
| `doGacha` | ブラウザ抽選＋Firestore更新 | サーバー抽選＋原子更新＋再送重複排除 |
| `recordMatchResult` | ブラウザで戦績と報酬変更 | サーバーが戦績を確定し一回だけ付与 |
| `claimPendingAdminGrants` | ブラウザで申請済み配布反映 | サーバーが配布の真正性・受取済みを確認 |
| `claimOperationGifts` | ブラウザでギフト反映 | サーバーがギフト対象・期限と受取済みを確認 |
| `grantGems` / `grantPity` | ブラウザからユーザー更新 | 管理者権限確認を伴うサーバー操作 |

## セキュリティ境界

- Firestore Security Rules はブラウザの JavaScript を信用しない。画面上のボタン無効化やソース難読化は不正更新の対策ではない。
- サーバー管理用のサービスアカウント・秘密鍵を Hosting / JavaScript / 公開GitHubへ置かない。
- Cloudflare Workers Free 等の枠内に収める設計は別途必要。無料は保証できず、上限超過で動作停止する可能性がある。
- 現行ルール全文はこのリポジトリには存在しないため、差分マージと実動作のテストは未完了。
