# 0バト v1.2.0 — 10人・Spark無料プラン向けセキュリティ改善

## 対象と限界
- 目標は **アクティブプレイヤー約10人・Firebase Spark（月額課金なし）**。
- Cloud Functions / Blaze / 有料サーバーは導入しない。既存データの移行・削除もしない。
- **本バージョンだけで不正ガチャや無制限ジェム改ざんを完全に防ぐことはできません。** 現在のブラウザからの `users/{uid}` 更新を維持しているため、本人による不正データ変更は残る。
- Firestore本番のルールは **Firebase Hostingデプロイでは更新されない**。以下を管理者がFirebase Consoleで適用する必要がある。

## 今回GitHubへ実装したこと
1. 非公開デッキを保護するルールブロック（**本番ルールへの手動適用が必要**）：`security/v1.2.0_decks.rules.part`
2. 管理者配布予約 `admin_grant` は `visibility: "private"` として生成し、受取人UIDで読む。
3. 公開デッキ名・運営ギフト検索は `visibility=="public"` も条件とし、Firestoreのルールと整合させる。
4. ガチャの「表示クリア」が天井カウンター `gachaPity` を消してしまうバグを修正。
5. 旧対戦準備画面でルーム番号を「先に読む→あとで作成する」方式から、衝突を検出するトランザクション方式に変更。
6. Firebase Hostingへ安全系HTTPヘッダー（nosniff、Referrer-Policy、X-Frame-Options、Permissions-Policy、HSTS）を追加。
7. v1.2.0表示とキャッシュ対策、および無料プラン向け静的回帰チェックを追加。

## Firestoreルールの適用（要管理者操作）
1. [Firestore Rules](https://console.firebase.google.com/project/tcg-0bato/firestore/rules)を開く。
2. **現在のルール全文をバックアップ**。以前の管理者UID固定認証ルールも保持。
3. 既存の `match /decks/{deckId}` を丸ごと `security/v1.2.0_decks.rules.part` 内の同名ブロックに置き換える。
4. 他の `match` はそのまま。特に `/users`、`/rooms`、`/cards` には変更しない。
5. Firebaseコンソールで構文エラーがないか確認し、**公開**。
6. **同じパスに別の広い `allow read/write` ルールを残さないこと**。Firebaseルールは複数許可のOR評価。
7. ルールのプレイグラウンド、またはEmulatorで本人・他人のアクセスを検証する。

### Firestore Security Rulesの試験項目
| 対象 | 想定される結果 |
| --- | --- |
| 一般ユーザーAが自分の非公開デッキを取得・編集 | 許可 |
| AがBの非公開デッキを取得・編集・削除 | 拒否 |
| ログインしていない閲覧者が公開デッキを取得 | 許可 |
| 公開一覧クエリ：`where("visibility","==","public")` | 許可 |
| 非公開デッキを含む、無条件の一覧クエリ | 拒否 |
| 限定公開デッキをID指定で取得 | 許可 |
| 一般ユーザーが`type:"admin_grant"`のドキュメントを作成 | 拒否 |
| 本人が`where("targetUid","==",uid)`で自分への配布を取得 | 許可 |
| 管理者（認証済み）が配布・運営ギフトを作成 | 許可 |

※ルールの静的テストは導入済み。Firebase Emulatorと本番の実アクセス試験は **未完了**。

### リグレッション検証（実際の画面）
- 既存のUID、ジェム、Growth、所持カードが変化していない。
- 自分の「非公開」デッキを保存→閉じる→開く→読み込む。
- 「公開」デッキの閲覧とコピー。
- 管理者が運営配布を予約→対象ユーザーが受け取る。
- ガチャを1回使用して残高・所有カードを確認、「表示クリア」でも天井カウントが変化しない。
- PLAYで2端末から同時に同じルーム番号を作っても既存ルームが上書きされない。
- スマホとPCでカード一覧/デッキ内容切替、攻撃対象選択→決定/キャンセル。

### 復旧方針
- ルール変更後にエラーが起きたら、バックアップしたルールへ戻す。ソースのリリースとFirestoreルールの戻しは独立している。
- 管理者のメール認証や既存データは、切り分けまでログアウト／アプリデータ削除をしない。
- `deploy/live` の直前のコミット/Hostingリリースからロールバックできる。ユーザーデータを手動で初期化しない。

## 残存する高優先度リスク（完了扱いにしない）
1. **本人のジェム・Growth・所持カードの自由な書き換え**：`users/{uid}` を本人が書き換えられる現状は残る。
2. **ガチャ抽選の真正性**：`gacha.js` の`Math.random`はブラウザで実行され、サーバー検証ではない。
3. **勝敗・対戦報酬の真正性**：`user_store.js`の`recordMatchResult`もブラウザ実行。
4. **対戦ルームの書き込み権限**：参加者単位の厳密な書き込み制限は未実装。
5. **tierBoardsの共有更新権限**：旧ルールのままなら第三者編集可能。
6. **管理者アカウント**：メール所有確認、強いパスワード、できればMFAの設定を別途確認する。
7. **HTTPS CSP**：既存の多くのインラインJS/CSSとの互換性未検証なので、強制CSPは導入していない。
8. **無料枠**：Sparkは請求されない代わり、容量・通信・書込上限を超えるとサービス制限の可能性がある。

## 次の段階（管理者の承認と無料外部サーバーの設定が必要）
Firebase Sparkのまま不正ガチャ・報酬を防ぐには、信頼できる無料外部サーバー（例：Cloudflare Workers Free）を別アカウントで用意し、署名付きFirebase IDトークン検証・レート制限・秘密鍵の安全な保存・サーバー側の抽選／結果確定が必要。**クライアントからの資産直接更新をFirestoreルールで禁止するのは、サーバー移行が完了してから**。それ以前に禁止するとガチャ・報酬などが止まる。

Cloudflare Workers Freeにはリクエスト上限やCPU時間上限がある。無料運営を維持するには利用量監視・上限到達時の安全な停止設計が必要。
